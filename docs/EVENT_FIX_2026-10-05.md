# Event Controller fix, 2026-10-05 — handoff for the tactical session

Made on `main`, **not published on its own**. Jason will ship it with the tactical
update. Merge `main` into `tactical` to pick it up. It touches only the event files
plus one new file, none of which `tactical` has changed:
`EventSupport.cs` (new), `ThresholdEvents.cs`, `BooleanEvents.cs`,
`WeatherIntensityEvent.cs`, `WeatherTypeEvent.cs`.

**Report (Deapri, Workshop):** the custom events never trigger: an oxygen event wired
to a toggle did nothing. They also don't show their compared values or which output
is active, the way vanilla events do.

## Three causes, all fixed

1. **The events read GT_ terminal properties.** They read with
   `GetValueFloat("GT_…")`, but those properties only exist after the game has built an
   upgrade module's terminal in this session. On a dedicated server they never exist
   unless a Programmable Block asks (TerminalApi, ENGINE_TRAPS 18). Until then the read
   throws and becomes "no reading", so the event never fires. The block list also
   offered no instruments, because `IsBlockValidForList` used the same read.
   `WeatherTypeEvent` called `GetValueFloat` outside any try, so its whole tick threw
   every second.
   **Fix:** events read `GroundTruthSession.StateFor(block)` directly, and roles come
   from `Instruments`. Each expression mirrors its TerminalApi getter, with the property
   named in a comment beside it.
2. **`NotifyValuesChanged` cleared the latch.** Changing the threshold, condition, AND
   mode or On/Off made the next evaluation a "first" one, and a first evaluation never
   fires. Dragging the slider past the reading, which is how anyone tests, did nothing.
   Vanilla re-evaluates against the state it already holds and fires on a flip
   (decompiled `MyEventControllerGenericEvent.NotifyValuesChanged`). The latch is now
   kept. `AddBlocks`/`RemoveBlocks` still latch without firing, as vanilla's do.
3. **No info pane.** Vanilla writes it through `MyEventControllerGenericEvent`, which
   the whitelist prohibits. The new `EventPane` writes CustomInfo instead
   (`AppendingCustomInfo` + `RefreshCustomInfo`). It shows the event name,
   condition/threshold, each instrument's value (or `not working` / `no reading`) and
   `Output: 1 - <yes text>` / `2 - <no text>`. Every GT event component exists on every
   controller, so only the selected one writes, and it clears its text when deselected.
   Each client builds its own text; nothing goes over the network.

Firing goes through `EventSupport.Fire`, server only. Vanilla's `TriggerAction` was
already a no-op on clients (it checks `Sync.IsServer`); this just makes that explicit.

## Also noticed, NOT fixed

`GTEventWeatherType.SelectedType` (the weather-type dropdown) is a plain field. It is
set on whichever machine's terminal changed it and is not synced or saved, so on a
dedicated server the server always watches "any weather", and the choice is lost on
reload. That needs a sync and save path; it is a separate job.
